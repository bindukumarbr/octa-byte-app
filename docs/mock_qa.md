## 1. Opening & Architecture Overview

**Q: Give me a high-level walkthrough of this project.**

> So this is a full-stack transaction management app — React frontend, Node/Express
> backend, Postgres database. Honestly the application logic itself is simple,
> CRUD on a transactions table. Where I spent most of my time was the cloud side:
> I provisioned the whole thing on AWS with Terraform, put together a three-tier
> VPC, wired up ECS Fargate for compute, RDS for the database, and a GitHub
> Actions pipeline that builds, scans, and deploys it with zero manual steps.
> If it's useful I can start at the network layer and work up, or jump straight
> to whichever part you want to dig into.

**Q: Walk me through what happens when a user hits your site.**

> Request comes in to one Application Load Balancer. The ALB has a default rule
> that sends everything to the frontend target group, and one override rule —
> priority 10 — that catches anything under `/api/*` and sends it to the backend
> instead. Both the frontend and backend run as ECS Fargate tasks in private
> subnets, so they're not directly reachable from the internet, only through the
> ALB. The backend talks to RDS Postgres, which sits in its own isolated subnet
> with no internet route at all. Credentials for that database are never typed
> anywhere — they're generated by AWS and pulled from Secrets Manager at
> container startup.

**Q: What would you say is the single most important decision you made on this project?**

> Probably the three-tier subnet split — public, private, and an isolated
> database tier — instead of the simpler two-tier public/private model. It's one
> decision, but almost every other security choice I made is downstream of it.
> If I'd put the database in the same private subnet as the compute layer, a
> single security-group mistake could expose it. With three tiers, two separate
> mistakes have to happen before that's possible.

## 2. Networking — VPC, Subnets, Security Groups

**Q: Why three subnet tiers instead of two?**

> A flat public/private split puts ECS and RDS in the same private subnet. If a
> security group gets misconfigured, anything in that subnet can potentially
> reach the database directly. Splitting the database into its own isolated
> subnet — no internet gateway, no NAT route, nothing — means it's not just a
> security-group rule protecting it, it's the network topology itself. You'd
> need to mess up two independent things, not one.

**Q: Why two Availability Zones and not three?**

> Two is the minimum for actual high availability — if one AZ has an outage,
> the other keeps serving traffic. Three AZs would triple my NAT Gateway cost
> for a workload that doesn't need that level of resilience. It's a cost/
> availability trade-off and for this project two was the right call. For
> something with much stricter uptime requirements I'd reconsider.

**Q: Why security-group references instead of CIDR ranges?**

> Because Fargate tasks get a brand-new network interface — and a new IP —
> every time they redeploy. A CIDR rule like "allow 10.0.0.0/16" would work,
> but it allows anything in that address range, including stuff you add later
> that shouldn't have that access. Referencing the ALB's security group ID
> directly says "only traffic from this specific logical group," regardless of
> what IP it currently has. It's the difference between scoping by identity
> versus scoping by location.

**Q: What's a NAT Gateway doing here, and what does it cost?**

> ECS tasks live in private subnets, but they still need outbound internet —
> to pull images from ECR and call Secrets Manager and CloudWatch. The NAT
> Gateway lets them initiate outbound connections without being reachable
> inbound. Cost-wise it's roughly four and a half cents an hour plus a per-GB
> charge, so call it thirty-some dollars a month minimum. For dev or test
> environments the usual trick is a NAT instance instead — a small EC2 running
> a NAT AMI — way cheaper but you're managing it yourself.

**Q: (Pushback) Why not just put everything in public subnets and rely on security groups? Simpler, no?**

> It would be simpler, yeah, but you're putting all your eggs in one basket —
> the security group becomes your only line of defense. If that's misconfigured
> even once, the resource is directly exposed. Keeping compute and data off
> public subnets means the network topology itself is the first line of
> defense, before any security-group rule is even evaluated. I'd rather have
> two layers that both have to fail.

## 3. Security — Secrets Manager, IAM, OIDC

**Q: How does your backend get its database password without you ever setting one?**

> In the Terraform RDS module I set `manage_master_user_password = true`. That
> tells AWS to generate the password itself, store it in Secrets Manager, and
> handle rotation — I never touch it, it's never in a variable, never in the
> state file. On the ECS side, the task definition has a `secrets` block that
> maps that secret's ARN to the `DB_PASSWORD` environment variable, and the
> task execution role has a policy granting `GetSecretValue` on that one ARN.
> ECS resolves it before the container even starts, straight into memory.

**Q: Tell me about a real bug you hit with that setup.**

> Yeah, this one was annoying. The backend container kept crashing at
> start-up with AccessDenied on the secret. The root cause was simply that the
> task execution role had never been granted permission to read it — the ECS
> module only generates that policy if you pass the secret's ARN in
> `task_exec_secret_arns`. While I was debugging I also added a trailing
> wildcard to the ARN, because Secrets Manager puts a random six-character
> suffix on every secret ARN and I suspected a mismatch. Looking back, the
> module's output ARN already includes that suffix, so the wildcard is
> probably unnecessary — I kept it as a harmless safety net and haven't
> re-tested without it. The painful part was that AccessDenied doesn't tell you
> *why* — missing permission or wrong resource — so you end up guessing.

**Q: What's the difference between a task role and a task execution role?**

> Execution role is used by ECS itself, before your code even runs — pulling
> the image from ECR, fetching secrets, writing logs. Task role is what your
> application code uses at runtime to call other AWS services. In this project
> the backend doesn't call AWS APIs directly, so the task role doesn't need
> anything special — all the Secrets Manager permission lives on the execution
> role.

**Q: Why OIDC instead of storing AWS keys as GitHub secrets?**

> Long-lived access keys sitting in GitHub secrets are a standing risk — if the
> repo's ever compromised, those keys are valid until someone notices and
> rotates them manually. With OIDC, GitHub issues a short-lived signed token for
> each workflow run, AWS verifies it against GitHub's own OIDC provider, and
> hands back temporary credentials that expire when the job ends. A leaked
> token from a finished run is worthless. The only AWS-related thing stored
> as a GitHub secret is the account ID, which isn't even a credential — the
> one other secret is the Slack webhook URL for failure alerts, which has no
> AWS access at all.

**Q: What's the story behind the sub claim in your trust policy?**

> This is actually a pretty recent GitHub change. My trust policy's condition
> checks the `sub` claim on the OIDC token, and it used to be a name-based
> format — `repo:owner/reponame`. GitHub moved to an immutable format that
> embeds the numeric owner and repo IDs instead, so even if a repo gets deleted
> and recreated with the same name, the old trust policy won't accidentally
> match the new repo. I actually hit this directly — my first version used the
> name-based format and kept failing, so I pulled the actual JWT from a failed
> run, decoded it, and matched my policy to the real claim.

**Q: (Pushback) Is that wildcard on the secret ARN a security risk?**

> I get why it looks that way, but not meaningfully. Everything before the
> `*` is this one secret's full ARN — its unique name plus AWS's random
> suffix — so the wildcard can only match ARNs that start with that exact
> string. No unrelated secret can match. And honestly I think the wildcard is
> unnecessary anyway; I'd test removing it on the next apply and drop it if
> the task still starts.

## 4. Compute, Routing, Database

**Q: Why ECS Fargate instead of EC2 or EKS?**

> Against EC2-based ECS: Fargate means no nodes to patch, no capacity planning,
> no spot-interruption handling — I define CPU and memory per container and
> AWS runs it. Against EKS: Kubernetes gives you a lot of powerful primitives,
> but for a two-service app on a single cloud, that operational overhead —
> cluster upgrades, node groups, the learning curve — isn't earned. The honest
> trade-off is Fargate costs more per vCPU than EC2 would at scale. For a small,
> bursty workload like this, that's the right trade to make.

**Q: When would you actually reach for EKS?**

> When you need Kubernetes-native tooling that doesn't really exist in ECS —
> something like Istio for service mesh, or Argo CD for GitOps — or if you're
> running multi-cloud or hybrid and portability across platforms actually
> matters. For a single, AWS-native app like this one, ECS is just simpler.

**Q: Why one ALB instead of separate load balancers for frontend and backend?**

> Two ALBs means two DNS names, and now your frontend needs to know the
> backend's hostname — which changes per environment and opens up CORS
> headaches. One ALB with path-based routing gives you one origin: default
> action goes to the frontend, and a higher-priority rule catches `/api/*` and
> sends it to the backend. Same browser origin, no CORS, and it's half the ALB
> cost.

**Q: Why not Nginx proxy-passing to the backend instead of the ALB doing it?**

> That's actually exactly what broke in production. In my original local
> docker-compose setup (it isn't committed to the repo) containers shared a
> network with built-in DNS, so Nginx's `proxy_pass
> http://backend:4000` just works. In ECS with awsvpc networking, each task
> gets its own network interface — there's no "backend" hostname for Nginx to
> resolve unless you explicitly set up Service Connect. I ended up ripping the
> Nginx proxy out entirely and letting the ALB do the routing instead, since it
> already has visibility into both target groups anyway.

**Q: Why managed RDS instead of running Postgres yourself on EC2?**

> Self-hosting means you're on the hook for backups, replication, failover, OS
> patching — all of it. RDS Multi-AZ handles failover automatically, promoting
> a standby in a different AZ in under two minutes with zero code changes. I
> should be upfront that my instance is single-AZ to save cost — Multi-AZ is
> `multi_az = true` and the first thing I'd switch on for real availability.
> For a project like this, reimplementing what RDS already gives you for
> free isn't a good use of time.

**Q: How does the database schema actually get created? There's no migration tool here.**

> Right, there's no Flyway or Liquibase. RDS gives you a completely blank
> database — unlike local Docker, which can run init scripts automatically.
> What I did instead: `index.js` wraps startup in an async IIFE that reads
> `schema.sql` and runs `CREATE TABLE IF NOT EXISTS` before calling
> `app.listen()`. If that query fails, it calls `process.exit(1)` — the server
> never starts in a broken state. It's idempotent, so every boot after the
> first one is a no-op.

**Q: (Pushback) That's a bit unusual — why not a proper migration tool?**

> Totally fair, and for a schema with more than one table or any real
> evolution over time, a migration tool is the right call — version history,
> rollbacks, safe team collaboration. For this project it's a single table and
> the operation is idempotent by construction, so a dedicated tool felt like
> more infrastructure than the problem justified. If this grew past a handful
> of tables I'd bring one in immediately.

## 5. CI/CD Pipeline

**Q: Walk me through the pipeline, end to end.**

> Three jobs, strictly sequential. First, test-and-scan runs on every PR and
> push — installs dependencies, runs the Jest suite, runs `npm audit` at
> high severity. If that fails, nothing downstream happens. Second, on a push
> to main only, build-and-push builds both Docker images, tags them with the
> git commit SHA, scans them with Trivy, and pushes to ECR. Third,
> deploy-production pulls the live task definition from ECS, swaps in the new
> image URI, and deploys — but only after someone manually approves it in
> GitHub's environment protection rules.

**Q: Why tag images with the git SHA instead of `latest`?**

> `latest` is mutable — you push to it and it overwrites whatever was there, so
> you can't tell what code is actually running just from the tag. The SHA
> traces a running container back to an exact commit instantly. It also makes
> rollback trivial — the previous ECS task definition revision still points at
> the old SHA image, so rolling back is just forcing a new deployment with that
> revision, no rebuild needed.

**Q: Why run Trivy if you already have `npm audit`?**

> `npm audit` only looks at your Node dependency tree — it has no idea what's
> in the base OS image. Trivy scans the whole container, including the Alpine
> or Debian packages underneath. OS-level CVEs are a real attack surface that
> `npm audit` just can't see.

**Q: I notice Trivy's exit code is set to 0. Doesn't that mean it doesn't actually block anything?**

> Correct, and that's a deliberate trade-off I'll own rather than hide. Right
> now it reports findings but doesn't fail the build. The production-correct
> setup is exit-code 1 on CRITICAL findings — but that needs a documented
> waiver process alongside it, otherwise a base-image CVE with no available
> patch yet blocks every deploy indefinitely. I'd rather name that as a known
> gap than pretend it's fully gated.

**Q: What happens if a newly deployed container fails its health check?**

> ECS won't drain the old tasks until the new ones pass the ALB health check,
> so if the new version fails, the rollout just stalls — old tasks stay in
> service, users never see downtime. But ECS doesn't auto-rollback; someone has
> to notice and force a redeploy of the previous task definition revision. A
> more mature setup would wire a CloudWatch alarm to a Lambda that does that
> automatically.

## 6. Terraform / Infrastructure as Code

**Q: Why Terraform registry modules instead of writing raw resources?**

> Hand-rolling a VPC alone is 20-plus resources — subnets, route tables,
> associations, the NAT gateway, the EIP — with a lot of subtle wiring that's
> easy to get slightly wrong. The community modules encode AWS best practices
> and have been reviewed by a huge number of people. The honest risk with
> modules is using one you haven't actually read — so for every module here I
> read the source before relying on it, which is actually how I found that the
> ECS module defaults to a read-only root filesystem, which is what crashed
> Nginx.

**Q: Why native S3 locking instead of the classic DynamoDB approach?**

> DynamoDB locking was the only option before Terraform 1.10. From 1.10
> onwards you can lock natively using S3's conditional-write feature — no
> extra table to provision or pay for. This project pins Terraform to 1.11+,
> so using DynamoDB here would just be carrying forward a pattern the tooling
> has already moved past.

**Q: What actually happens under the hood with `use_lockfile`?**

> Before any apply touches state, Terraform tries to create a lock file in S3
> with a conditional PUT — "only write this if it doesn't already exist." If
> it doesn't exist, this run gets the lock. If it does, the run is rejected
> immediately. Because that conditional PUT is atomic, even two applies
> starting at the exact same millisecond can't both win. Lock file gets deleted
> when the apply finishes.

**Q: What if an apply gets killed before it releases the lock?**

> Then the lock file just sits there in S3 forever, and the next apply fails
> with "error acquiring the state lock." The fix is `terraform force-unlock`
> with the lock ID, which just deletes that file — but you only do that once
> you're certain nothing else is actually running, otherwise you've defeated
> the whole point of locking.

**Q: Why pin the AWS provider to `~> 6.0` instead of leaving it open?**

> That's the pessimistic constraint operator — it allows any 6.x release but
> blocks a jump to 7.0. A major version bump can change resource arguments in
> breaking ways, and I don't want a CI run three months from now to silently
> pull in a breaking provider version on `terraform init` with zero code
> changes on my end.

## 7. Observability

**Q: What's your monitoring setup, and why CloudWatch over something like Datadog?**

> ECS logs go to CloudWatch Log Groups automatically through the awslogs
> driver, no agent needed, into 30-day log groups. Container Insights gives
> CPU/memory/network at the task and service level, RDS metrics feed my
> alarms (Performance Insights isn't enabled — that's a natural next step),
> and I built two dashboards — one application-focused, one
> infrastructure-focused. The assignment's requirement was tool-agnostic, and
> CloudWatch satisfies all of it with zero extra infrastructure to run or pay
> for. Datadog or Grafana would genuinely give richer dashboards and
> correlation, but that's an extra platform to deploy and bill for, and for
> this deliverable it wasn't justified.

**Q: Why two dashboards instead of one?**

> Partly because the assignment explicitly asked for at least two, but more
> importantly they serve different audiences. The application dashboard —
> request rate, 5XX count, latency, a live log tail — is what a developer
> wants when something's acting up. The infrastructure dashboard — ECS and RDS
> CPU, memory, connection count — is what you'd actually check if you're doing
> capacity planning or on-call triage.

**Q: Why alarm on RDS connections specifically?**

> Postgres has a hard connection ceiling based on instance class — for
> `db.t3.micro` it's around 85. Each ECS task runs its own connection pool, so
> if a bunch of tasks scale up at once, you can actually exhaust that limit
> and start getting connection errors that have nothing to do with the
> database being overloaded, just out of connections. Alarming at 80 gives
> early warning. The real fix at scale is something like PgBouncer sitting in
> front of RDS to multiplex connections.

**Q: Have you worked with Prometheus or Grafana?**

> Not hands-on in production — CloudWatch was the right call for this
> project's requirements specifically. I understand the model conceptually,
> pull-based scraping, PromQL, how Grafana visualizes whatever data source you
> point it at — but my actual production experience on this stack is
> CloudWatch.

## 8. Backend Application Code

**Q: Why is the DB schema init wrapped in an async IIFE in `index.js`?**

> Because I need to `await` the schema query before calling `app.listen()`,
> and top-level await isn't available in CommonJS — `require`-based modules.
> Wrapping the whole startup sequence in `(async () => {...})()` is the
> standard way to get async/await at the top level of a file like this.

**Q: Why does schema init have to run before `app.listen()`, specifically?**

> If I called `listen()` first, Express starts accepting connections
> immediately, and there's a real race — a request could hit `/api/transaction`
> before the `CREATE TABLE` query finishes, and it'd fail with "relation
> transactions does not exist." Running the schema query first and only
> calling `listen()` inside the success path guarantees the table exists before
> any traffic is accepted.

**Q: Why `process.exit(1)` on failure instead of just logging the error?**

> Because if I only log and let the server start anyway, the ALB hits `/health`
> and gets a 200 — Express itself is fine, it's only the DB layer that's
> broken — and now the ALB is happily routing real user traffic to a container
> that 500s on every request. Calling `process.exit(1)` makes the failure loud
> and immediate: ECS marks the task unhealthy, the ALB stops routing to it, the
> deployment fails visibly instead of silently serving garbage.

**Q: Why is `ssl: { rejectUnauthorized: false }` in `db.js`? Isn't that insecure?**

> RDS enforces SSL by default — without any SSL option at all, the `pg` client
> tries an unencrypted handshake and RDS rejects it outright, that's actually
> how I found this needed to be here in the first place. `rejectUnauthorized:
> false` means the connection is encrypted, but the client doesn't validate
> RDS's certificate against a CA bundle — so you're protected from passive
> eavesdropping but not from a man-in-the-middle presenting a fake cert.
> Given RDS has no public route and lives in an isolated subnet, that practical
> risk is low. The fully hardened version downloads the actual AWS RDS CA
> bundle and sets `rejectUnauthorized: true`. In a compliance context like PCI
> or HIPAA I wouldn't accept the current setting.

**Q: Tell me about the relationship between `index.js` and `app.js`.**

> `app.js` defines the Express app itself — middleware, routes, error handling
> — and exports it. `index.js` owns everything about actually starting the
> process: validating env vars, running the schema init, calling
> `app.listen()`, handling graceful shutdown on SIGTERM. `index.js` requires
> `app.js` rather than redefining any of it, so there's exactly one definition
> of the routes, and the test suite — which imports `app.js` directly without
> touching a real database — is testing the literal object that gets served in
> production.

**Q: (Pushback, if they already know) Was that always true, or did you find something?**

> Good catch if you're asking that — no, I actually found and fixed this
> during a code-quality pass. `index.js` used to redefine every route itself
> instead of requiring `app.js`, so they were two independently maintained
> copies of the same app. They'd already drifted — the `/health` handler in
> `index.js` returned a plain string, while `app.js`'s returned `{status:
> "ok"}`, which is what the test actually asserts. The test suite was green,
> but it was only proving something about `app.js`, not about what
> `node index.js` — what the Dockerfile actually runs — was serving. I
> refactored `index.js` to require `app.js` instead of duplicating it, so now
> there's one definition and the tests actually cover the deployed path.

**Q: Why mock the database and the service layer in your tests instead of hitting a real Postgres?**

> Two reasons. Practically, there's no Postgres running in the GitHub Actions
> runner, and I mock only the service layer — the one place that touches the
> database — so the real connection pool is never even loaded. (I used to mock
> the pool and the env check too, but I ran the suite with those removed and
> it passed, so they were redundant.) More importantly,
> these tests are specifically about whether Express routing, middleware, and
> status codes behave correctly — not about whether the SQL is right. Mocking
> the service layer isolates that. They're really integration tests of the
> HTTP layer, not unit tests of a single function, and they're not DB
> integration tests either — that'd be the next layer to add, probably with
> something like `pg-mem` or a real Postgres container in CI.

## 9. "Tell Me About a Bug" / Debugging Stories

**Q: Tell me about the hardest bug you had to debug on this project.**

> Probably the OIDC trust policy failure, because the error message gives you
> almost nothing — just "not authorized to perform AssumeRoleWithWebIdentity."
> My trust policy's `sub` claim condition was using the old name-based format,
> and GitHub had already migrated to an immutable ID-based format for this
> account. I ended up pulling the actual JWT from a failed workflow run,
> decoding it on jwt.io to see exactly what GitHub was really sending, and then
> matched my Terraform condition to that. The lesson was: when a cryptographic
> trust check fails, don't guess at the format — go look at the actual token.

**Q: Walk me through a bug that took multiple attempts to fully fix.**

> Getting the frontend running in ECS, honestly. First it crashed because
> Nginx's `proxy_pass` was pointing at a hostname, `backend`, that doesn't
> resolve in ECS's networking model the way it does in docker-compose. Fixed
> that by removing the proxy and letting the ALB route `/api/*` directly. Then
> it crashed again — different error — because the ECS module defaults
> containers to a read-only root filesystem, and Nginx needs to write to
> `/var/cache/nginx` on startup. Two separate root causes that looked like the
> same symptom, "frontend container keeps dying," from the outside.

**Q: Tell me about a time your infrastructure and your pipeline disagreed with each other.**

> There was a window where a local `terraform apply` and a GitHub Actions
> deploy ran close together and stepped on each other. The pipeline grabbed
> the current task definition — which still had a broken environment variable
> name — built the real image, and deployed. Then I ran `terraform apply`
> locally, which fixed the environment variable but also reset the container
> image back to the placeholder, since that's what main.tf still said. I had to
> trigger an empty commit to get the pipeline to run one more time and pick up
> both fixes together. It taught me to be disciplined about never applying
> Terraform and triggering a deploy at the same time without thinking through
> which one "wins."

## 10. `challenges_faced.md` — One Q&A Per Numbered Item

> This section maps 1:1 to the 16 entries in `docs/challenges_faced.md`, in the
> same order. If the interviewer says "tell me about a bug you ran into" and
> you want a specific one on demand rather than the general stories in Section 9,
> this is the lookup table.

**Q: (Challenge 1) Your ECS task couldn't read the DB secret at first — what was going on?**

> The Terraform ECS module doesn't automatically grant the task execution role
> permission to read a secret just because the secret exists — you have to
> explicitly tell it to, via `task_exec_secret_arns`. I'd wired the `secrets`
> block on the container definition but forgotten that variable, so ECS had no
> IAM policy letting it call `GetSecretValue` at all. Added the ARN to
> `task_exec_secret_arns` in the service definition and the policy got
> generated correctly.

**Q: (Challenge 2) You mentioned a wildcard "gotcha" on the secret ARN — what exactly happened?**

> Even after wiring things up, it still failed with AccessDenied, and my
> working theory was the random six-character suffix Secrets Manager adds to
> every secret ARN — something like `-eq2ug9` — so I appended a `*` to the
> ARN in the IAM policy. To be straight about it: the module's output ARN
> already includes that suffix, so the wildcard was most likely not the real
> fix — granting the permission in the first place was. I kept the `*` as a
> harmless precaution and I'd test removing it on the next apply.

**Q: (Challenge 3) There was a crash loop around an environment variable name — what happened there?**

> Once the IAM side was fixed, the task pulled the secret successfully and then
> immediately crashed with exit code 1. CloudWatch logs showed "missing
> required environment variable: DB_PASSWORD." The Terraform `secrets` block
> was injecting the value under the name `DB_PASS`, but the app's env
> validation strictly required `DB_PASSWORD`. Simple naming mismatch — fixed
> the `name` field in the `secrets` block to match exactly what the app
> expected.

**Q: (Challenge 4) You mentioned Terraform and your pipeline stepped on each other — walk me through that.**

> Classic race condition between two independent deploy paths. The GitHub
> Actions pipeline ran first, pulled the *current* live task definition —
> which still had the broken `DB_PASS` name — injected the real image, and
> deployed that. Then I ran `terraform apply` locally, which fixed the
> variable name but also reset the container image back to the Terraform
> placeholder, since that's literally what `main.tf` said at the time. End
> result: correct env var, wrong image. I fixed it with an empty commit
> (`git commit --allow-empty`) to force the pipeline to run one more time and
> pick up both the fix and the real image together.

**Q: (Challenge 5) The frontend crashed with "host not found in upstream backend" — what was that about?**

> Nginx's config had `proxy_pass http://backend:4000/`, which works fine
> locally because docker-compose gives containers a shared network with
> built-in DNS — `backend` resolves to the right container. ECS Fargate uses
> `awsvpc` networking, where each task gets its own network interface and
> there's no such hostname unless you explicitly set up Service Connect. I
> removed the Nginx proxy block entirely — the ALB's path-based routing
> already sends `/api/*` straight to the backend target group, so the proxy
> was redundant anyway.

**Q: (Challenge 6) Then the frontend crashed again on a different error — what was that?**

> `mkdir /var/cache/nginx/client_temp failed: read-only file system`. The
> `terraform-aws-modules/ecs/aws` module defaults every container to a
> read-only root filesystem as a security hardening measure, which Node
> tolerates fine but Nginx doesn't — it needs to write its cache and PID file
> on startup. Correct fix is mounting a small writable tmpfs volume just for
> `/var/cache/nginx` and `/var/run`, keeping the rest of the filesystem
> read-only. Current state in this project actually has the whole filesystem
> writable — a trade-off I'd tighten up given more time.

**Q: (Challenge 7) You had a 404 on "Cannot GET /api/transaction" — what caused that?**

> The ALB forwards anything under `/api/*` to the backend, but it doesn't
> strip that prefix before forwarding — the backend receives the full path
> including `/api`. My Express routes were defined as just `/transaction`, not
> `/api/transaction`, so nothing matched. Fixed by prefixing every backend
> route with `/api` to match what the ALB actually sends.

**Q: (Challenge 8) There was a 500 error about "no pg_hba.conf entry... no encryption" — what's that?**

> The `pg` client was trying to connect to RDS without SSL, which works fine
> against a local Postgres container but RDS enforces encrypted connections by
> default and rejects plaintext handshakes outright. Added
> `ssl: { rejectUnauthorized: false }` to the pool config in `db.js` to allow
> the SSL handshake. It's encrypted but doesn't validate RDS's certificate —
> a known, named trade-off, not an oversight.

**Q: (Challenge 9) Then a 500 saying the "transactions" relation doesn't exist — how'd that happen?**

> RDS gives you a completely blank database on creation — Terraform
> provisions the instance, but nothing runs the actual `CREATE TABLE`.
> Locally, docker-compose can run SQL init scripts automatically on container
> start; RDS has no equivalent. The fix was making `index.js` read `schema.sql`
> and run it with `CREATE TABLE IF NOT EXISTS` before calling `app.listen()`,
> so the table is guaranteed to exist before any request can hit it.

**Q: (Challenge 10) There was a 404 on DELETE for a specific transaction ID — what was wrong there?**

> The route was literally written as `app.delete('/api/transaction/id')` —
> the string "id", not an Express path parameter. So it only matched a
> request to the exact URL `.../transaction/id`, never `.../transaction/2` or
> any real ID. On top of that, the validation middleware was reading the ID
> from `req.body.id` instead of `req.params.id`, so even a correctly-matched
> route would've validated the wrong field. Fixed both: route became
> `/api/transaction/:id`, and the handler and middleware read from
> `req.params.id`.

**Q: (Challenge 11) You mentioned your tests weren't actually testing what got deployed — tell me about that.**

> Right — `index.js`, which is what `node index.js` and the Dockerfile
> actually run, and `app.js`, which is what the test suite imports, had become
> two independently maintained copies of the same Express app instead of one
> requiring the other. They'd already drifted: `index.js`'s `/health` handler
> returned a bare string, `app.js`'s returned `{status: "ok"}`, and the test
> asserts on `.status`, so it was only ever proving something about `app.js`.
> A green test suite wasn't proof the deployed route behaved that way. I
> refactored `index.js` to require `app.js` instead of redefining every route,
> so now there's a single source of truth and the tests cover the exact object
> that ships.

**Q: (Challenge 12) You said you found a security group bug while adding comments — what happened?**

> While restructuring `main.tf` to add explanatory comments, the ECS security
> group's catch-all egress rule ended up nested inside the `ingress_rules` map
> instead of its own `egress_rules` block. The Terraform security-group module
> decides a rule's direction by which variable you pass it into, not by the
> rule's name — so despite being named `egress_all`, it silently became an
> *inbound* rule allowing all protocols from `0.0.0.0/0` into the ECS security
> group. That directly undercuts the three-tier defense-in-depth design the
> rest of the infrastructure is built around. Caught it by reviewing my own
> diff against the committed version rather than trusting that I'd only
> added comments — `terraform validate` would have passed either way, since
> the rule is perfectly valid HCL in the wrong place. Moved the rule back
> into its own `egress_rules` block.

**Q: (Challenge 13) Your dashboard has a log widget. Does it actually show logs?**

> It would not have, and I found that during an audit. My monitoring file
> declared its own log groups, but the ECS module creates a log group for each
> container itself, named `/aws/ecs/<service>/<container>`, and that's where
> the logs actually go. The widget was querying my hand-made, permanently
> empty group. I deleted the unused groups, set 30-day retention on the
> container definitions, and pointed the widget at the module's group by
> reference so the name can't drift. I confirmed it in `terraform plan`.

**Q: (Challenge 14) Does the app run locally?**

> It does now. After I moved the API routes under `/api` for the ALB, my Vite
> dev proxy still had a rewrite that stripped `/api`, so every local call
> hit `/transaction` and got a 404. I removed the rewrite and verified it by
> running the real Express app and the real Vite dev server together: calls
> through the proxy return 200 and 201, and the old stripped path returns 404.
> I also added a `DB_SSL=false` switch for local Postgres; production still
> defaults to SSL on.

**Q: (Challenge 15) Can your frontend containers talk to the database?**

> They could, originally, and that was a flaw. Both services shared one
> security group, and the RDS group trusted it, so the static Nginx containers
> inherited database access. I split it into a frontend group and a backend
> group, each accepting traffic only from the ALB on its own port, and made
> RDS trust only the backend group. The plan shows the database rule
> referencing just the backend group.

**Q: (Challenge 16) Tell me about a time `terraform validate` passed but the config was broken.**

> The ALB module version. Someone — me, while adding comments — loosened the
> pin from `10.5.1` to `~> 9.0`. My listener-rule syntax only exists in the v10
> module, and `validate` passed because the module's inputs are loosely typed.
> It only failed at `terraform plan` with "Insufficient action blocks". I
> restored the exact version with a comment explaining why. The lesson is that
> `validate` checks syntax, not whether a module will accept your values, so
> I always run a `plan` before trusting a change. I'll also admit I had wrongly
> signed it off earlier on the strength of `validate` alone.

## 11. Closing / What Would You Do Differently

**Q: If you had another week, what would you add or change?**

> Three things, in priority order. First, HTTPS — right now it's port 80 only,
> no ACM certificate, which is fine for an assignment but not for anything
> real. Second, the Trivy exit code — I'd flip it to actually block on
> CRITICAL findings and put a waiver process next to it. Third, I'd replace
> `rejectUnauthorized: false` with full certificate validation using the AWS
> RDS CA bundle. None of these are hard, they just weren't the highest priority
> given the time I had.

**Q: What's the weakest part of this project, in your own opinion?**

> Honestly, before today it would've been that my test suite wasn't actually
> testing the code that got deployed — `index.js` and `app.js` had drifted
> into two separate copies of the same app. I caught and fixed that during a
> review pass, but it's a good example of how easy it is for "tests are green"
> to quietly stop meaning what you think it means if you're not careful about
> single-sourcing your code.

**Q: Is there anything you'd flag as a known limitation, unprompted?**

> Yeah — single NAT gateway, so if that AZ has an issue, outbound internet
> access for ECS tasks in the other AZ goes with it, even though the tasks
> themselves are still up. For true AZ-level resilience you'd want one NAT per
> AZ. I made the single-NAT trade-off deliberately for cost, but it's worth
> naming rather than letting you find it yourself.

**Q: Anything else you want to add before we wrap up?**

> Just that every piece of this was something I built, broke, and fixed myself
> against a real AWS account — not copied from a tutorial and left alone. I'm
> happy to pull up any specific file, run `terraform plan` live, or go deeper
> on anything that's most useful for you to see.
